REVIEW WORKTREE RULE

A reviewer must inspect the candidate implementation, not the old `master`.
Use one of these safe arrangements:

1. Pause the implementation session and open a separate read-only session in
   the same candidate worktree; or
2. Commit the candidate on its feature branch and create a review worktree at
   that exact candidate commit.

Do not create a reviewer worktree from `master` unless the candidate has already
been merged there.

REVIEW HANDOFF PACKAGE

Before launching a reviewer, the implementation session should provide:

- candidate commit or exact working-tree path;
- starting/base commit;
- concise change summary;
- specification and report paths;
- commands already run and their results;
- browser URL and how to select deterministic cases;
- screenshot, contact-sheet and video paths;
- known limitations;
- any issue on which independent judgment is specifically wanted.

READ-ONLY MEANS READ-ONLY

Reviewer sessions may:

- inspect source and diffs;
- review architecture, numerical contracts, tests and resource lifecycle;
- run tests, type checking and builds;
- launch the app;
- use the visible developer-tools launcher;
- use query parameters as deterministic deep links;
- capture temporary evidence outside tracked source;
- report findings with exact file and line references.

Reviewer sessions must not:

- edit production code, tests, specifications or reports;
- run formatters that rewrite files;
- commit, merge, rebase, push or open pull requests;
- “fix” findings themselves;
- expand the round’s scope.

DEVELOPER-TOOLS UX ACROSS ALL STAGES

The ocean round establishes a shared compact `Tools` or `Debug` launcher. It
must expose existing World/General and Buoyancy diagnostics plus Ocean without
requiring query parameters. Camera and Graphics add their own panels in later
rounds.

Every stage preserves:

- a single visible, discoverable launcher during early development;
- a one-action `Hide all` clean view;
- lazy loading of closed diagnostic panels;
- optional query-parameter deep links for bookmarks, test automation and
  deterministic captures;
- one shared UI state rather than competing debug systems.

INTEGRATION CHECK

Do not integrate a stage until:

- its full tracked test suite, type check and production build pass;
- the implementation prompt’s own browser, performance and internal-critic loop
  is complete;
- documentation and evidence match the actual final candidate;
- the diff contains no unrelated work.

The separate companion reviews are an additional post-round quality pass, not a
dependency that leaves the implementation agent waiting for you. You may run
them before integration, or after integration on the exact completed commit and
then open a small follow-up improvement branch.

FOLLOW-UP IMPROVEMENT HANDOFF

For a fresh follow-up session, prepend the original implementation prompt and
then add:

“The original implementation round and its internal visual-review loop are
complete. This is a bounded follow-up improvement pass on that completed
candidate. Read the attached external code-and-visual review report(s), verify
each finding against the current code and evidence, and rank them by correctness
and impact. Implement only accepted in-scope fixes; do not redo the architecture
or expand the feature set. Re-run the affected deterministic cases, the full
tracked test suite, type checking, production build and browser checks.
Regenerate equivalent before/after evidence and update the round report with
findings accepted, rejected and fixed.”

Use Codex/Sol for the ocean follow-up. For camera and graphics, keep Claude/Opus
as the sole follow-up integrator when visual judgment dominates; use Codex/Sol
instead for a narrowly technical follow-up, but do not have both edit the same
candidate concurrently.
